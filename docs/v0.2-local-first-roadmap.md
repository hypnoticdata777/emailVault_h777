# v0.2 Local-First Roadmap

This roadmap turns Email Vault from a one-thread preservation POC into a usable
local Gmail offloader and inbox cleaner while keeping the architecture ready for
a later subscription SaaS.

## Product Goal

Let a user connect Gmail, preview a batch of messages, export selected messages
to storage they control, verify the saved copies, and then optionally clean
Gmail with label/archive actions. Trash/delete remains deferred until Free Space
Mode has review, warning, and reversibility protections.

## Architecture Choice

Build local-first before hosted SaaS:

- fewer Google verification blockers during personal/private use;
- easier direct export to PC, USB, or OneDrive-synced folders;
- safer iteration against synthetic data and the user's own inbox;
- cleaner later path to SaaS because the export, routing, review, and cleanup
  boundaries can be lifted into hosted workers.

The SaaS-ready boundary is still important. Do not mix user interface decisions,
Gmail API access, export verification, and cleanup mutation into one large
module. Each step should be independently testable.

## v0.2 Milestones

1. Export Package Schema
   - Define the portable export package contract.
   - Include raw `.eml`, attachments, metadata JSON, optional readable HTML/PDF,
     manifest/checksum files, and normalized text.
   - Keep sender-controlled values out of storage paths.

2. Local Storage Target
   - Accept a user-selected filesystem root.
   - Support PC folders, USB drives, external drives, and OneDrive-synced
     folders through the same path-based boundary.
   - Refuse unsafe paths and record enough metadata to prove where exports went.

3. Domain And Category Routing
   - Generate folder routes from sender domain, predefined category, or a mixed
     layout.
   - Start with explainable rules: sender domain, sender address, newsletter
     headers, no-reply patterns, Gmail labels/categories, attachment presence,
     and user overrides.
   - Classify messages as newsletter, automated, bank/financial, human,
     needs-review, attachments-heavy, or unknown.

4. Dry-Run Review
   - Show what would happen before any Gmail cleanup.
   - Report counts by category, sender domain, planned export path, and planned
     Gmail action.
   - Default unknown and risky messages to needs-review.

5. Preserve Mode
   - Export and verify messages.
   - Leave Gmail unchanged.
   - Produce manifests/checksums that later cleanup modes can rely on.

6. Clean Inbox Mode
   - Require verified export first.
   - Apply label and archive after review.
   - Mark-read can be a separate toggle.
   - Record cleanup outcome without claiming Gmail storage was reduced.

7. Free Space Mode
   - Defer initial implementation until Preserve Mode and Clean Inbox Mode are
     stable.
   - Require explicit opt-in, warnings, dry-run review, export verification, and
     trash/reversibility window.
   - Permanent delete should not be added until Gmail API behavior, consent copy,
     and private validation are complete.

8. Portable AI/Data Port
   - Export normalized text, metadata JSON, manifests, checksums, and attachment
     paths.
   - Avoid coupling Email Vault to one AI tool.
   - Let users point their own AI, search, knowledge-base, or research tooling at
     the saved folders.

## First Implementation Tickets

1. Add export package domain contracts.
2. Add route planning for sender-domain and category folder layouts.
3. Add synthetic fixtures for newsletter, no-reply automated, bank, human,
   attachments-heavy, and unknown messages.
4. Add classifier rules with deterministic tests.
5. Add dry-run review objects with counts and planned actions.
6. Add local export package writer with checksum manifest tests.
7. Wire Preserve Mode through the existing storage verification boundary.
8. Add Clean Inbox Mode intent records while Gmail mutation remains disabled.

## SaaS Later

The hosted subscription version should add:

- user accounts and billing;
- production Google OAuth verification;
- tenant-isolated storage and audit records;
- hosted workers for sync jobs;
- user dashboards and review queues;
- privacy policy, Limited Use disclosure, deletion process, and security review
  preparation;
- admin controls for export targets, retention, and Gmail cleanup policies.

The local-first implementation should avoid assumptions that would make this
hard later.
